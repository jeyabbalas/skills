## Arrays instead of swarm

FRCE has no `swarm` ([Biowulf differences](https://ncifrederick.cancer.gov/staff/FRCE/Documentation/UsageGuides/BiowulfFRCEdifferences)), and its docs don't mention job arrays; plain Slurm arrays (`sbatch --array`) work as upstream describes.

- Each task queues, runs, and counts against the user's caps as a separate job.
- Arrays fit independent commands of similar size, and replace a shell loop of `sbatch` calls (JOBS.md (Scheduler etiquette)). One command: JOBS.md. Steps that depend on each other: a workflow manager (WORKFLOWS.md (Choosing an approach)), or arrays chained by dependencies ([Dependencies on arrays](#dependencies-on-arrays)).

## Array template

The commands file is your deliverable: one complete command per line, generated by a script, with absolute paths, its own output and log, steps joined by `&&`, and a guard that skips a line whose output exists, so a rerun never redoes finished work (`mytool` is a placeholder):

```bash
# on the compute node (inside your session) — adapt the tool, flags, and paths
p=/scratch/cluster_scratch/$USER/proj; mkdir -p "$p/out" "$p/logs"
: > "$p/commands.txt"                    # truncate: regenerating must not append
for f in "$p"/in/*.fq.gz; do
  s=$(basename "$f" .fq.gz)
  echo "[ -s $p/out/$s.bam ] || { mytool -t \$SLURM_CPUS_PER_TASK -i $f -o $p/out/$s.tmp.bam && mv $p/out/$s.tmp.bam $p/out/$s.bam; } > $p/logs/$s.log 2>&1" >> "$p/commands.txt"
done
wc -l < "$p/commands.txt"; head -n 2 "$p/commands.txt"
```

The escaped `\$SLURM_CPUS_PER_TASK` expands in each task, not in your loop; the lines as written assume file names without spaces. The array script, saved as `/scratch/cluster_scratch/$USER/proj/array.sh`, runs line N as task N:

```bash
#!/bin/bash
#SBATCH --job-name=align
#SBATCH --partition=norm
#SBATCH --nodes=1
#SBATCH --cpus-per-task=4
#SBATCH --mem=16g
#SBATCH --time=02:00:00
#SBATCH --output=logs/%x_%A_%a.out
set -euo pipefail
source /etc/profile.d/modules.sh 2>/dev/null || true
module load mytool/1.2
TMPDIR=$(mktemp -d "/scratch/local/${USER}_${SLURM_JOB_ID}_XXXX"); export TMPDIR   # JOBS.md (Temporary files)
trap 'rm -rf "$TMPDIR"' EXIT
cd /scratch/cluster_scratch/$USER/proj
line=$(sed -n "${SLURM_ARRAY_TASK_ID}p" commands.txt)
[ -n "$line" ] || { echo "no line ${SLURM_ARRAY_TASK_ID} in commands.txt" >&2; exit 1; }
echo "task ${SLURM_ARRAY_TASK_ID} on $(hostname -s): $line"
bash -o pipefail -c "$line"
```

- `%A` is the array's job ID and `%a` the task index; `logs/` must exist before submission.
- `-o pipefail` because a child shell doesn't inherit the script's: without it, a piped line (`bwa … | samtools sort …`) whose first stage fails still ends `COMPLETED`. Piped stages run at once, so their threads together must fit `--cpus-per-task`.
- The `--array` range goes on the command line, computed from the file, so the two always match. Indices start at 1 because `sed` numbers lines from 1.
- Each task reads its line when it starts, possibly hours after submission: don't edit or regenerate `commands.txt` until the array, and any rerun by index, has finished.

Run the line with the largest input in your session first, which needs a session started with `--cpus-per-task` so the line's variable is set (its peak memory: MONITORING.md (Sizing the next run)), then check the script:

```bash
# on the compute node (inside your session)
cd /scratch/cluster_scratch/$USER/proj
line=$(sed -n 17p commands.txt); time bash -o pipefail -c "$line"
bash -n array.sh && sbatch --test-only --array=1-3 array.sh
```

Hand over a pilot, then the rest:

```bash
# on the FRCE login node — the user runs:
cd /scratch/cluster_scratch/$USER/proj
sbatch --array=1-3 array.sh                            # pilot: check logs/ and out/ before the rest
sbatch --array=4-$(wc -l < commands.txt)%20 array.sh   # the rest, at most 20 tasks at once
```

## Sizing and throttling

- Resources are per task, and every task gets the same, so size for the largest input (MONITORING.md (Sizing the next run)). If input sizes vary widely, split the file into a small-input and a large-input array.
- The user's per-partition CPU cap (JOBS.md (Partitions and walltime)) bounds concurrency: at most cap ÷ CPUs per task run at once, fewer while the user's other jobs and sessions hold CPUs; the rest pend with a limit reason.
- Throttle with `%N` (`--array=1-500%20`) to leave room for the user's other work and to spare shared storage: `/scratch/cluster_scratch` is one network share for everyone, and hundreds of I/O-heavy tasks slow it for all. Start I/O-heavy arrays at 10–20. The user can change a running array's limit: `scontrol update JobId=JOBID ArrayTaskThrottle=10`.
- Walltime is per task, and a `norm` array whose `--time` is 30 minutes or less runs in `short`, under its smaller cap (JOBS.md (Partitions and walltime)).
- FRCE's `MaxArraySize` is 20002 (live, Sept 2026: `scontrol show config | grep MaxArraySize`), so indices run up to 20001. It caps the highest index, not just the count, so a longer file needs bundling ([Bundling short tasks](#bundling-short-tasks)) or several arrays with an offset:

```bash
# in array.sh, instead of the plain sed line
n=$(( SLURM_ARRAY_TASK_ID + ${OFFSET:-0} ))
line=$(sed -n "${n}p" commands.txt)
```

```bash
# on the FRCE login node — the user runs (for a 30,000-line file):
sbatch --array=1-20000%20 array.sh
sbatch --array=1-10000%20 --export=ALL,OFFSET=20000 array.sh
```

## Bundling short tasks

Every task pays for queueing, node setup, and module loading, and counts against the user's limits; thousands of tasks that last seconds cost more than they compute. Aim for tasks of at least 10–15 minutes.

**Several lines per task, one after another.** For N lines at K per task, submit `--array=1-$(( (N + K - 1) / K ))` and give `--time` K times one line's time:

```bash
# in array.sh, replacing the sed, echo, and bash -c lines
K=10
first=$(( (SLURM_ARRAY_TASK_ID - 1) * K + 1 ))
rc=0
while IFS= read -r line; do
  bash -o pipefail -c "$line" < /dev/null || { echo "FAILED: $line" >&2; rc=1; }
done < <(sed -n "${first},$(( first + K - 1 ))p" commands.txt)
exit "$rc"
```

`< /dev/null` keeps a command from swallowing the lines still to be read; a failed line is logged, the rest still run, and the task ends `FAILED`.

**Several lines at once, on one node.** For many single-threaded lines, one job (or one task per chunk of the file) with C CPUs runs C lines at a time:

```bash
# in the job script; request --cpus-per-task=C and --mem for C lines at once
tr '\n' '\0' < commands.txt | xargs -0 -n 1 -P "$SLURM_CPUS_PER_TASK" bash -o pipefail -c
```

xargs runs every line and returns non-zero if any failed, so `set -e` fails the job at the end. Each line must use one thread, or set `-P` to CPUs ÷ threads per line. GNU `parallel`, a system binary rather than a module (MODULES.md (Finding software); check `parallel --version` in your session), adds a job log: `parallel -j "$SLURM_CPUS_PER_TASK" --joblog run.log < commands.txt` runs the lines, and the same command with `--resume-failed` reruns only the failed ones.

## Failures and reruns

One read-only query finds the failed tasks (yours to run); the second line prints their indices as an `--array` list, such as `3,7,12,150-200`:

```bash
# on the compute node (inside your session) — read-only, once
sacct -j JOBID -X -n -P -o JobID,State,ExitCode,Elapsed,NodeList | awk -F'|' '$2 != "COMPLETED"'
sacct -j JOBID -X -n -P -o JobID,State | awk -F'|' '$2 ~ /FAIL|TIMEOUT|OUT_OF_MEMORY|CANCELLED|DEADLINE|PREEMPTED/ {id = $1; sub(/^[0-9]+_/, "", id); gsub(/[][]/, "", id); sub(/%.*/, "", id); print id}' | paste -sd, -
```

1. **Read the causes.** The state says why (`OUT_OF_MEMORY`, `TIMEOUT`, `FAILED` with an exit code; meanings: JOBS.md (Exit codes and job states)). The task's Slurm log is `logs/NAME_JOBID_INDEX.out`, and the line's own log names its input. Failures clustered on one node point at the node (TROUBLESHOOTING.md (Job killed or failed)).
2. **Check outputs, not only states.** A task ends `COMPLETED` whenever its line's last command succeeded, so compare expected outputs with what exists.
3. **Fix before rerunning.** Reproduce a failed line in your session (`sed -n 7p commands.txt`); memory or time kills need a larger `--mem` or `--time`. A whole array that failed the same way needs the fix, not a rerun.
4. **Rerun only those indices** against the unchanged `commands.txt`; the guards make any finished line exit at once:

```bash
# on the FRCE login node — the user runs:
cd /scratch/cluster_scratch/$USER/proj
sbatch --array=3,7,12 --mem=24g array.sh     # flags on the command line override the script's
```

The rerun gets a new array job ID, so its logs get new names.

## Converting a Biowulf swarmfile

A swarmfile's lines become `commands.txt`: join continued lines, drop comments and `#SWARM` lines, then find what only Biowulf has.

```bash
# on the compute node (inside your session)
awk '/\\$/ {sub(/\\$/, ""); buf = buf $0; next} {print buf $0; buf = ""}' old.swarm | grep -v -E '^[[:space:]]*(#|$)' > commands.txt
grep -n -E 'lscratch|/data/|/fdb/|SWARM_|module ' commands.txt   # lines that need FRCE paths or names
```

In the flagged lines, `/lscratch/$SLURM_JOB_ID` becomes `$TMPDIR` (the array script makes it); `/data/...` becomes the data's FRCE location (moving it: TRANSFER.md); `/fdb` paths become FRCE's reference data (APPLICATIONS.md); module names and versions become FRCE's (MODULES.md). The options become the array script's flags:

| swarm | FRCE array |
|---|---|
| `-g G` (GB per line) | `--mem=Gg` |
| `-t T` (threads per line) | `--cpus-per-task=T`; lines read `$SLURM_CPUS_PER_TASK` |
| `-b B` (lines per subjob, one after another) | K = B lines per task ([Bundling short tasks](#bundling-short-tasks)) |
| `-p P` (single-threaded lines at once) | `--cpus-per-task=P`, `--mem` for P lines, and `xargs -P` ([Bundling short tasks](#bundling-short-tasks)) |
| `--time T` (per line) | `--time` per task, times K when bundled |
| `--partition P` | an FRCE partition (JOBS.md (Partitions and walltime)) |
| `--gres=gpu:TYPE:N` | `--partition=gpu --gres=gpu:TYPE:N` with FRCE's types (JOBS.md (GPUs)) |
| `--gres=lscratch:N` | dropped; the per-task `$TMPDIR` replaces it |
| `--module a/1,b/2` | `module load` lines in the script, with FRCE's names, pinned |
| `--logdir DIR`, `-J NAME` | `--output=DIR/%x_%A_%a.out`, `--job-name=NAME` |
| `--maxrunning N` | `%N` in `--array` |
| `--dependency`, `--sbatch "OPTS"`, `#SWARM` lines | the same options as `#SBATCH` lines or `sbatch` flags |
| `--devel` | `bash -n array.sh` and `sbatch --test-only --array=1-3 array.sh` |
| `--joblog`, `--err-exit` | a log per line; `&&` inside lines |

- Set every resource: swarm's defaults (1.5 GB and one thread per line, a default walltime) don't carry over, and FRCE's are far larger (JOBS.md (Flags and defaults)).
- swarm bundled automatically beyond 1,000 subjobs; here, bundle short lines yourself, and offset beyond the highest index ([Sizing and throttling](#sizing-and-throttling)).
- CPUs are counted differently on the two clusters (JOBS.md (Flags and defaults)): treat a Biowulf `-t` as a starting point, and measure the pilot.

## Dependencies on arrays

A dependency on the array's job ID covers every task; the general types are in JOBS.md (Dependencies).

| Dependency | The dependent job starts when… |
|---|---|
| `afterany:ARRAYID` | every task has ended, in any state |
| `afterok:ARRAYID` | every task succeeded; after one failure it never runs |
| `afternotok:ARRAYID` | every task ended and at least one failed |
| `aftercorr:ARRAYID` | (the dependent is an array) its task N, once task N of the first array succeeded |
| `afterok:ARRAYID_7` | task 7 succeeded |

- After a large array, prefer `afterany` and have the next step check which outputs exist: under `afterok`, one failed task makes it unrunnable, and FRCE cancels it (JOBS.md (Dependencies)).
- `aftercorr` chains per-sample steps without waiting for the whole first array; both arrays must use the same indices.

```bash
#!/bin/bash
# submit.sh — the user runs it on the FRCE login node: bash submit.sh
set -euo pipefail
cd /scratch/cluster_scratch/$USER/proj
n=$(wc -l < commands.txt)
a1=$(sbatch --parsable --array=1-${n}%20 step1.sh)
a2=$(sbatch --parsable --array=1-${n}%20 --dependency=aftercorr:$a1 step2.sh)
sbatch --dependency=afterany:$a2 collate.sh      # collate.sh checks which outputs exist
```

## Stale advice on the official pages

- FRCE calls Biowulf's documentation "largely applicable" ([Biowulf differences](https://ncifrederick.cancer.gov/staff/FRCE/Documentation/UsageGuides/BiowulfFRCEdifferences)), but hpc.nih.gov's "Use swarm instead of job arrays" ([ExpUserGuide, do's](https://hpc.nih.gov/docs/ExpUserGuide.html#dos)) and every app page's swarm section assume a command FRCE lacks → convert them ([Converting a Biowulf swarmfile](#converting-a-biowulf-swarmfile)).
- The hpc.nih.gov FAQ's recipe for rerunning failed subjobs ([swarm_select](https://hpc.nih.gov/docs/FAQ.html#swarm_select)) reads `jobhist`, which FRCE doesn't document, and swarm's per-subjob `cmd.N` files, which exist only with swarm → `sacct` and `--array` with the failed indices ([Failures and reruns](#failures-and-reruns)).
